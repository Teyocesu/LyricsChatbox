# LyricsChatbox

## v0.7.0 normative proposal — Composition, Decorations and Daily-Use Clarity

v0.7.0 is a Windows-only .NET 10 WPF minor release with exactly four product areas: Display/composition simplification, a local Decorations picker, profile-owned Rotating Messages, and an About/sidebar/Output presentation cleanup. It preserves the current local-first architecture and the pipeline Playback → Track identity → Lyrics → Composition → Formatting → Scheduler → OSC. It adds no account, backend, telemetry, cloud state, runtime scraping, arbitrary player, plugin system, scripting engine or generic Chatbox framework.

Implementation status: Phases 0–3 are implemented on the v0.7.0 development branch. Phase 3 supplies the shared Insert picker and prospective-output diagnostics only; the Phase 4 Display redesign and rotation editor remain unimplemented.

### Display and composition

- Display answers one question — “What should VRChat show?” — through five visible concepts: Profile, Composition, Lyric Context, Presentation and Live Preview. Existing presets and profile behavior remain available; Custom is the primary advanced editor rather than a separate template ecosystem.
- The supported composition tokens remain `{lyrics}`, `{title}`, `{artist}`, `{album}`, `{time}`, `{message}`, `{elapsed}` and `{duration}`. Each token is an accessible insertable chip. Activating a chip replaces the current selection, or inserts at the current caret when the selection is empty, subject to the editor's existing 512 UTF-16-unit maximum. Focus returns to the editor and the caret moves after the inserted token. Substituted values continue to be single-pass data and are never reinterpreted as template syntax.
- Status/Rotating Messages controls are shown only when the effective composition consumes `{message}`: always for Status / Time, and for Custom only when its template contains that exact supported token. Other presets show no large active no-op editor. A concise disabled explanation may tell the user to add `{message}`.
- Lyric Context controls are enabled only when the effective composition consumes `{lyrics}`. The same derived-state refresh runs during cold initialization, profile selection, preset changes and template edits, eliminating the v0.6.2 cold-start inconsistency without a separate bug-specific subsystem.
- Left, Center and Right remain presentation choices. Center and Right continue to be approximated with ordinary spaces and are never described as pixel-perfect VRChat alignment. Floating/Compact also remains a presentation choice and retains the existing 142-visible-unit budget plus suffix; normal output retains 144 visible UTF-16 units. Live Preview remains the actual formatted visible payload, not an optimistic editor rendering.

### Insert / Decorations

- The three editor-specific ASCII selectors are replaced by one reusable `Insert…` picker used by Custom composition, Status/Rotating Message editors and the Manual draft. One insertion routine owns caret/selection replacement, maximum-length checks, focus restoration and caret restoration; no editor-specific copy exists.
- Navigation is Popular, Symbols, Text Art, Kaomoji, Dividers, Frames, Hearts, Music, Status, Favorites and My items. Search performs a simple case-insensitive in-memory match over name and content, with an optional Kind filter. The exact Kinds are `Symbol`, `TextArt`, `Kaomoji`, `Divider`, `Frame`, `Heart`, `Music` and `Status`. Symbols use a dense grid, Kaomoji and short snippets use compact rows/cards, Dividers use wide previews, and Text Art/Frames use monospaced multiline cards. The UI must not force every type into the same large card.
- A built-in item has only stable ID, display name, Kind, content and an optional Popular flag. The bundled versioned JSON is immutable at runtime, no larger than 1 MiB, contains at most 256 entries, has unique IDs of at most 64 allowlisted characters, uses only known Kinds, limits names to 40 UTF-16 units and content to 512 UTF-16 units and nine explicit lines, and contains valid plain Unicode text with no disallowed control characters. Built-in decorations do not contain supported composition-token syntax. Invalid bundled data makes the picker unavailable with bounded UI feedback; it never blocks startup or output, and there is no duplicate code-owned catalog.
- Favorites are an ordered set of at most 128 built-in or user-item IDs; stale and duplicate IDs are ignored. My items contain stable local ID, Name, Content and one lightweight display type. They are capped at 64 entries; IDs are at most 64 allowlisted characters, names at most 40 UTF-16 units and content at most 512 UTF-16 units/nine explicit lines. There are no editable tags, ratings, recently-used subsystem, inspectors, duplication workflow, cloud sync, sharing or remote catalog.
- Picker activation proposes raw text insertion; it does not create a composition template. Destination semantics remain authoritative, so deliberate token text inserted into Custom is interpreted only by the existing Custom composer. Decorations do not own or persist complete layouts.
- A prospective insertion is measured through the existing composition, alignment and `ChatboxFormatter` path for its originating editor. The picker shows the resulting visible-unit/line cost and a clear warning when the current final payload would be truncated. Source art is never silently rewritten or truncated in storage or in the editor. Editor `MaxLength` may reject an insertion; final OSC safety remains solely `ChatboxFormatter`'s responsibility. No second formatter exists.
- Search receives initial focus when practical; Tab and arrow navigation remain logical; Enter inserts the selected item; Escape closes; accessible names describe symbol entries where practical; focus and caret return to the originating editor after insert or cancel.
- Built-ins may use project-composed short arrangements, requester-provided examples, common short status phrases and individual Unicode symbols without claiming ownership over generic material. Inspiration sites are not content sources. Any external dataset included must be pinned, reviewed item-by-item, carry its copyright/license and provenance in `THIRD_PARTY_NOTICES.md` plus any required bundled license, and be covered by packaging tests. There are no runtime Internet requests. The MIT-licensed `kaomojikan/kaomoji-data` repository remains an eligible research candidate for a later curated subset, not approval to ship its catalog or unrelated website collections.

### Rotating Messages

- Rotation changes only the value supplied to the existing `{message}` token. It never rotates whole templates, adds a `{rotation}` token, or sends output directly. A profile owns one `MessageRotation` with schema version 1, `Enabled`, `IntervalSeconds` and ordered `Items`; each item has stable ID, Text and Enabled. Order is sequential only.
- A profile has at most 16 rotation items. Item IDs are unique within the profile and at most 64 allowlisted characters. Text is plain Unicode, at most 512 UTF-16 units and nine explicit lines. Allowed intervals are exactly 5, 10, 15, 30, 60 and 120 seconds; new/migrated state defaults to 15 seconds. Sub-second intervals, random/weighted order, conditions, schedules, scripts and external data are out of scope.
- The existing profile `Message` field remains only the backward-compatible legacy mirror, never the current runtime rotating value. A v0.6.2 profile with `Message = "Hello!"` loads as a disabled rotation with one enabled item containing exactly `Hello!`; the visible result remains exactly `Hello!` and no automatic rotation starts. Empty Message yields no item. On configuration save only, Message becomes the first enabled configured item's exact text or empty when none is enabled. Timer advancement never writes `DisplayProfile.Message`, `AppSettings.Message`, `settings.json` or `profiles.json`.
- `ProfileLibrary` remains schema version 1 because the optional nested rotation is additive and old JSON remains valid. The nested object carries its own version. Missing rotation migrates in memory deterministically and is serialized on the next ordinary profile save; unrelated profile values and the selected profile are unchanged. A syntactically readable but invalid nested rotation normalizes only that profile's rotation to the safe disabled legacy-Message state. A syntactically unreadable `profiles.json` retains the current whole-library fallback to AppSettings migration; neither case resets AppSettings or unrelated LocalData.
- Runtime timing/index state is per profile and session-only. App launch or first activation starts at the first enabled item with a full interval. Inactive profiles freeze their remaining interval. No current index, deadline or fractional remaining time is persisted.
- Rotation advances only while automatic output is eligible: master Output is On, no Output Pause is active, Manual does not own output, and the effective composition consumes `{message}`. Output Off, Output Pause, Manual ownership, inactive profile and absent `{message}` freeze the remaining interval. Resume continues that remainder; it does not reset or catch up through queued outputs.
- If the app sleeps or stalls while otherwise eligible past a deadline, the runtime advances exactly one item and starts one full interval from the current monotonic time. It never cycles through multiple missed intervals, and composition exposes only that one current value. The existing 1.05-second `ChatboxScheduler` alone owns pacing, dedupe and retry; the rotator has no output dependency and never calls `ChatboxOutput.Send()`.
- Track identity, track changes, lyric changes and lyric timing never reset or advance rotation. Switching profiles activates that profile's frozen state. Zero enabled items supplies the legacy Message fallback (normally empty after a v0.7.0 configuration save) and does not tick. One enabled item is observably identical to today's static Message and does not trigger repeated payloads.
- Editing the current item updates its visible value without resetting its remaining interval. Reordering retains the current item by ID and its remaining interval. Adding an item does not reset. Deleting or disabling the current item selects the next enabled item in post-change order and starts one full interval. Enabling rotation starts at the first enabled item with a full interval; disabling it returns to the deterministic fixed Message mirror. Disabled items are skipped.
- The editor supports add, edit, delete, reorder and per-item enable/disable. Decorations can be inserted through the shared picker. The UI is a small list, not a playlist manager, and is inactive with truthful guidance when `{message}` is not consumed.

### Persistence, safety and migration

- `AppSettings` remains versionless and unchanged by the new feature models. Existing output, appearance, playback source, OSC and lifecycle values survive byte-for-value-equivalent deserialization/serialization behavior. Quick Messages, corrections, manual matches/ignore state, lyric cache and all other LocalData remain unchanged.
- Profile rotation is the optional versioned nested profile data described above. The `profiles.json` read cap increases from 160 KiB to 2 MiB so the existing maximum 20 profiles can each hold the new bounded worst-case lists, including JSON escaping, without weakening item/count validation. Decoration user state lives in a separate atomic `decorations.json`, schema version 1, maximum 256 KiB, containing only Favorites and My items. It follows existing LocalData temp-and-replace writes. Missing, unsupported, oversized or malformed decoration state falls back to empty Favorites/My items only; it never resets profiles or settings. A failed read never deletes or automatically overwrites the bad file; the next explicit decoration save may atomically replace it.
- All persisted IDs, counts, enums, numeric ranges, string lengths, file sizes and explicit line counts are validated. User and bundled decoration/message text is plain text only. NUL, invalid UTF-16 and C0/C1 controls other than LF are rejected or normalized before persistence and again by the existing final formatter; no content is executed, interpreted as HTML, used as a file path or sent to a shell.
- Resource loading is local, size-bounded and version-checked. No catalog or user text causes a network request. External links are fixed and HTTPS. OSC receives only the output of the existing grapheme-safe formatter and scheduler. The release adds no secret or sensitive-data storage.
- Rolling back to v0.6.2 preserves the fixed `Message` mirror and ignores the additive rotation property. Saving a profile from v0.6.2 may discard unknown v0.7.0 rotation JSON, so rollback instructions must advise backing up LocalData or avoiding profile edits before returning to v0.7.0. Decoration state remains isolated and ignored by old builds.

### Normative acceptance invariants

- Existing v0.6.2 users retain selected profile, Custom template, Message, alignment, Floating/Compact, Lyric Context, appearance, Output, PlaybackSource, corrections, manual matches, lyric cache and runtime state. No unrelated reset occurs.
- Automatic output always follows Rotator value → existing composer/context → existing alignment → existing formatter → existing scheduler → existing OSC output. There is one scheduler, one formatter, no rotation send path and no queue of missed values.
- Output Off, Output Pause and Manual ownership cannot transmit rotation changes or accumulate replay. Re-entry exposes at most one latest desired automatic state at normal scheduler cadence.
- Preview and sent visible payload use the same composition/formatting result. Normal/floating budgets, nine-line limit, grapheme safety, whitespace semantics, suffix behavior, alignment and existing lyric-context candidate order remain unchanged.
- The picker never mutates stored art to fit and never implies oversized art will be fully visible. Catalog persistence corruption is isolated; profile rotation corruption is isolated to the affected profile's rotation.
- Keyboard insertion, picker cancellation, navigation, external-link failure, clipboard failure and small-window sidebar operation remain usable and non-crashing.
- Deterministic tests cover the rotation transition table, no-backlog boundaries, migrations, catalog validation/search/persistence, caret insertion, budget warnings, contextual Display state, About/navigation/link failures and all Output presentation states. Physical QA is required before release with real upgraded v0.6.2 state; real VRChat transmission stays disabled during development QA and loopback OSC is used when transmission verification is necessary.

### Explicitly out of scope

OBS, webhooks, Discord Rich Presence, Spotify Web API/OAuth/Connect, additional playback sources, production seek, overlays, hotkeys, cloud sync, accounts, online decoration downloads/marketplace/community sharing, plugin architecture, scripting, full rotating templates, conditional/random/weighted/scheduled rotation, telemetry, a database, full-text search and a general asset-management system are not part of v0.7.0.

Research basis: MagicChatBox's Personal Status demonstrates the user value of cycling status text, not an architecture to copy (https://github.com/BoiHanny/vrcosc-magicchatbox). VRChat's official Chatbox OSC reference retains the 144-character/nine-line contract, while the 2026.2.1 notes document the current five-messages-per-five-seconds bucket and automatic-message exception; LyricsChatbox conservatively keeps its existing 1.05-second scheduler (https://docs.vrchat.com/docs/osc-as-input-controller ; https://docs.vrchat.com/docs/vrchat-202621). Candidate external catalog data must have an auditable compatible license; `kaomojikan/kaomoji-data` is MIT but far larger than this release needs (https://github.com/kaomojikan/kaomoji-data). Unicode licensing applies to Unicode data/code points, not to copying a third-party site's curated art collection (https://www.unicode.org/policies/licensing_policy.html).

## v0.6.0 approved extension — Multi-player + Daily Use

Current product scope is Windows-only .NET 10 WPF with **Apple Music for Windows and Spotify Desktop for Windows** as the only explicitly supported music sources. The latter shipped in v0.6.0 for the physically observed Microsoft Store desktop client through documented GSMTC; other Spotify distributions remain unverified. The public stable v0.6.0 application supports both players. Both players share the existing player-independent TrackIdentity, local LRC/cache, LRCLIB then NetEase strict resolver, corrections, manual matches/ignore state, profiles/context, Chatbox composer and Unicode/grapheme/144-unit/nine-line/Compact/Floating budgets, latest-state-wins 1.05-second OSC scheduler, OSCQuery and manual ownership. Playback source never enters the persistent TrackIdentity key or v0.5.1 legacy migration.

Source choices are Apple Music, Spotify and Automatic. Automatic is the default whenever no valid explicitly saved choice exists; explicit Apple Music, Spotify and Automatic choices persist unchanged. Explicit choices inspect only that source, with no fallback to the other. The source badge always agrees with the accepted playback snapshot: a valid snapshot is never labeled not detected, and "not detected" means a genuinely absent compatible session rather than any transitional null. Automatic selects the sole Playing supported source; both Playing is ambiguous and fails closed with truthful guidance to choose explicitly. If both are Paused, an already bound valid source may remain during that run, but cold start with multiple paused sessions must not guess. Source selection enumerates GSMTC sessions, never treats GetCurrentSession() as authoritative. Existing v0.5.4 settings migrate to explicit Apple Music and fresh installs also default to Apple Music. A source switch invalidates the clock, automatic epoch/lookup, stale artwork, transport capabilities and volume association before fresh authoritative state; it does not discard manual Chatbox ownership or a draft.

The source boundary has exactly two adapters, not arbitrary-player discovery. Each identifies its own unambiguous GSMTC session, normalizes only physically justified metadata, reports raw playback/track/timeline observations and player-specific capabilities, and invalidates on loss or inconsistency. The shared epoch, lyrics, synchronization, output and artwork consumers remain source-independent. Apple Music retains its observed artist `" — "` album fallback only when AlbumTitle is empty and the split is unambiguous. Spotify's verified SourceAppUserModelId is `SpotifyAB.SpotifyMusic_zpdnekdrzrea0!Spotify`; do not broadly match names or assume unmeasured installers. Artwork uses only the selected GSMTC Thumbnail with existing byte/decode/revision bounds; no CDN/API or persistence. Volume remains a selected-player Core Audio association, never master volume. Transport is capability-driven. **Production seeking remains unsupported**; Phase 0's Spotify position changes were isolated research, not a product decision.

Timing is source-specific. Apple Music retains the v0.5.4 2-second freshness, 1.25-second discontinuity tolerance, rate sanity, integer-position ceiling, paused freeze and re-anchor behavior. Spotify Phase 0 measured 269 samples over one healthy 62.124-second recording, 15 fractional Positions, 4.611/4.617-second median/p95 authoritative changes, 4.512-second maximum observed playing LastUpdatedTime age and at most 0.124-second complete-cycle progression residual. A **5.25-second** Spotify freshness horizon is implemented for Phase 2: it exceeds measured p95 change cadence by 0.633 seconds and maximum observed age by 0.738 seconds, covering roughly one 225 ms poll plus additional bounded margin. It fails closed beyond that horizon; evidence does not prove rare stalls are safe. Playing interpolates only from fresh authoritative Position/LastUpdatedTime at sane rate and re-anchors periodically; Paused freezes; Resume requires a new playing anchor; no indefinite extrapolation or Apple integer ceiling for observed fractional Spotify anchors. Do not globally increase Apple's horizon.

Spotify's natural transition reset Position and changed EndTime about 0.23 seconds before the new Title. On an authoritative discontinuity inconsistent with normal same-track progression, the selected adapter must immediately emit invalidation so old automatic timing/lyrics become unusable and the automatic epoch advances. A duration change or near-zero reset with old metadata cannot bind the new timeline to that old TrackIdentity. Settle only after a later observation of the same selected source/session has usable title/artist, valid Position within Start/End, consistent duration/metadata and fresh state/timestamp; if metadata still looks old or the sequence is ambiguous, remain invalidated. No arbitrary multi-second sleep. Observed scrubs/restarts likewise invalidate immediately and require a later coherent anchor before resuming. Every old-source asynchronous result remains epoch/revision rejected.

Phase 3 implements Output Pause for 5, 15 or 30 minutes, until the accepted TrackIdentity changes, or until explicit resume. Pause is distinct from master Enabled and gates all automatic/manual/Live Edit/typing sends at the shared output boundary while playback monitoring, arbitration, timing, lyrics, artwork and UI continue. Entry persists first, clears Chatbox text and typing once best-effort when Enabled, and never stacks; replacement changes the one pause state. Timed pauses persist an absolute UTC expiration. Until-next-track persists only the exact TrackIdentity hash and ignores invalidation, reconnect, pause/resume, scrub and same-recording source switches. Indefinite pause survives restart. Resume never replays a backlog; automatic output uses only the latest state at normal cadence, while Manual ownership and drafts remain unsent and intact.

Better Startup State uses a separate atomic `runtime-state.json` containing only normal restore bounds, desired Normal/Maximized state, stable top-level section ID and Output Pause state. It never stores song metadata, lyrics, artwork, drafts, errors or listening history. Geometry is validated and clamped against current monitor work areas through a testable policy; invalid, missing-monitor, oversized and corrupt state falls back to a usable on-screen window. Minimized is never persisted as the desired visible state. Start Minimized applies before Show, can start hidden in the tray without a normal-window flash, and later tray/single-instance restoration uses the saved visible state and section. Packaging fix AUD-01 remains deferred and removes PLAN.md while preventing AGENTS.md/HANDOFF.md from shipping in portable/installer output.

v0.6.0 does not add playlists/queue/library browsing, Spotify Connect/Web API/OAuth/developer credentials, YouTube Music/Tidal/Deezer or arbitrary players/plugins; no cloud sync/accounts/backend/telemetry, OBS/local web API/remote companion, VR or desktop lyrics overlay/Mini Player/global hotkeys, translation/word karaoke/Sync Studio, third lyrics provider or automation/rules engine.

## v0.6.1 approved maintenance

- The profile defines the base content; Lyric Context only decides how much adjacent lyric context is added. The current lyric is mandatory whenever one exists. Candidates are tried in order — previous + current + next, then current + next, then previous + current, then current only — and the first candidate whose real final composed payload fits wins. Fixed profile/template content is never removed merely to fit optional adjacent lines; only a base payload that itself exceeds the budget falls back to safe truncation. A Custom template supports context through its `{lyrics}` token; templates without an effective `{lyrics}` token (including Status / Time) expose no context behavior and say so in the UI. An empty current lyric never yields a future lyric alone.
- Master Output Off is a hard no-transmission boundary: Send, Clear and Live Edit arm nothing while Off, drafts stay local and editable, and enabling output replays nothing. A new deliberate action after enabling may send. Typing never replays stale state. Output Pause keeps its own frozen-hold semantics and remains distinct from master Off.

## v0.5.3 approved maintenance
- Keep the 50 ms timing path for synchronization, lyric transitions, OSC scheduling, typing and manual ownership, while applying WPF presentation values only when their effective state changes. Playback progress may use an independent visual cadence; settings and profile changes remain immediate.
- Suppress repeated identical null Apple Music observations while preserving status/revision transitions, real-session loss and all real playback updates. Suspend clears stale transient playback without using resume semantics; resume invalidates old anchors and requests fresh authoritative state.
- Automatic OSCQuery retries every 30 seconds only while unresolved. A valid discovered destination stops periodic discovery until receiver, mode, lifecycle, manual request or destination invalidation makes discovery necessary again. Manual destination remains the fallback and discovery is not delivery acknowledgement.
- An explicit mouse or keyboard completion of a volume adjustment consumes the pending debounce once, while later or in-flight changes remain deliverable. Tray and second-instance restoration retain the last normal or maximized state and never remember minimized as the desired visible state.

## v0.5.2 approved maintenance
- Adaptive context is distinct from the explicit three-line mode. It keeps the current lyric, then uses available space for the next lyric, the previous lyric when the adjacent set fits, or song metadata when adjacent context does not fit. The explicit three-line mode continues to prefer previous, current and next together and removes lower-priority pieces only when required by the existing UTF-16, line, compact-suffix and grapheme limits. Custom and Status layouts do not use lyric context.
- Recovery guidance is hidden during lookup/fallback and for resolved or instrumental states. Ignored recordings offer Resume; missing, ambiguous and rejected matches offer useful recovery; temporary failures offer retry/recovery. Home has one context-sensitive action set. User-visible status text does not expose internal outcome or provider wording.
- Null Apple Music snapshots retain clear no-session, multiple-session and reconnecting/transition states. Empty previews use a distinct non-payload placeholder. All playback and candidate durations use m:ss below one hour and h:mm:ss from one hour onward.
- Update release notes are converted from bounded GitHub Markdown to deterministic safe plain text supporting headings, lists, emphasis and simple links, without HTML rendering or a browser view.

A user-requested installer download must use the project's official GitHub release, validate expected SHA256, and offer a separate explicit launch only after verification; mismatch/cancellation/failure never execute. Skip only suppresses automatic notification; manual checks still show the current release. No telemetry, automatic installation or signing credentials. Authenticode feasibility is investigated honestly and unsigned builds are not presented as trusted.

## Product and scope
A small Windows-only .NET 10 C# WPF application observes the selected Apple Music or Spotify Desktop source through Windows.Media.Control/GSMTC, resolves line-synchronized lyrics, follows authoritative playback timing and sends the current line to VRChat OSC. No accounts, credentials, telemetry, backend, arbitrary players, scraping, private player APIs, word karaoke or plugin framework. Independent implementation; no MagicChatBox source.

Single compact window: enabled control, source/track/artist, lyric, resolution status, offset (-5 to +5 seconds, positive means later: lyricTime = playbackPosition - offset), OSC host/port and concise degraded/error state. Settings persist locally; invalid settings fail safely; UI/network never block monitoring.

## Boundaries and responsibilities
The narrow playback-source boundary owns player-specific session identification, normalization, capability and timing policy. AppleMusicPlayback and SpotifyPlayback implement that boundary and enumerate their own exact unambiguous sessions (never blindly current session). PlaybackSourceCoordinator observes both candidates but permits only one selected PlaybackSourceHost to publish into the active pipeline. Preserve source/session identity, raw title/artist/album/track number, start/end/duration, reported Position, LastUpdatedTime, state/rate and local observation time. Keep normalized matching separate.

SynchronizationEngine uses source-specific timing policy with authoritative anchors plus bounded monotonic interpolation; never accumulate timer deltas indefinitely. Paused playback freezes. Reevaluate on pause/resume/observed scrub or restart/track change/discontinuity. Production does not initiate seeking. Missing/stale/unusable position fails closed.

Monotonically increasing track epoch invalidates lyrics before starting a new lookup. Session loss also invalidates. Async completions carry their initiating epoch; old success, error and cancellation cannot mutate the new track. Rapid changes and unchanged-track replay must be safe; reuse loaded lyrics where practical. Clean subscription/task disposal.

LyricsResolver order: exact local track-bound .lrc, validated flat cache, LRCLIB direct lookup, conservative search/scoring, no synchronized lyrics. Only timestamped lines qualify; instrumental and no lyrics are normal states. Normalize Unicode, case, spacing, punctuation and feature notation; preserve version annotations. Reject incompatible artist, duration or recording version and ambiguous candidates. Title alone is insufficient. LRC supports common timestamps, multiple tags, stable sorting, blank gap markers and metadata ignoring. Finite hold policy prevents lyrics hanging through instrumental gaps.

LRCLIB uses HTTPS, identifying User-Agent, sequential requests with spacing, bounded response/time, cancellation and Retry-After cooldown. Only necessary track metadata leaves the machine. Transient failure must not poison later tracks. Cache successes; corruption cannot prevent startup. Settings/cache under LocalAppData; no persistent full lyric history logs.

ChatboxOutput: default 127.0.0.1:9000, /chatbox/input (text, true, false). Preserve Unicode, conservatively cap at 144 UTF-16 units without splitting grapheme clusters, limit explicit lines, coalesce latest valid state, dedupe and pace sends. No stale retry queue. Disabling stops future lyric output immediately. UDP send success does not prove receiver presence or display. Receiver loss must not crash or build backlog; recovery sends current state only. Physical clearing/counting/pacing require client validation; tunables remain isolated.

## Decisions from the native spike
- Apple Music 1.1540 exposes source `AppleInc.AppleMusicWin_nzyj5cx40ttqa!App`. On two observed tracks, `Artist` is `artist — album`, `AlbumTitle` empty and TrackNumber 0. Split only one exact spaced em dash when AlbumTitle is absent; retain raw values.
- Normal playback emits timeline events about every 280ms (sometimes duplicates), with whole-second Position. The sampled timeline age during a 19s playing segment was 0.015–0.280s. Use 250ms fallback polling plus event wakeups, a 2s freshness horizon and a 1.25s quantization/discontinuity tolerance. Paused anchors ignore timestamp age; resume must reject an old paused timestamp until refreshed. These choices need seek and longer end-to-end validation.
- GSMTC TryChangePlaybackPositionAsync returned true for forward/back/restart without changing playback. The product only observes playback; physical seek testing must use Apple Music controls. Do not interpret a successful control call as an observed transition.
- OSC uses a narrow fixed-message encoder (aligned UTF-8 address/type/text with payload-free T/F tags), because this is smaller than a general OSC dependency. OSC format checked against https://opensoundcontrol.stanford.edu/spec-1_0.html ; no third-party implementation copied. UTF-8 is a receiver compatibility requirement beyond the old OSC 1.0 ASCII text wording. A 10s line-hold cap remains provisional. Output pacing was reduced from 1.5s to 1.05s after the user reported 1–2s transition delay. The 2026.2.1 live release documents five messages per five seconds; 1.05s spacing stays below that rate even without relying on the automatic-send exemption: https://docs.vrchat.com/docs/vrchat-202621 . Installed client is 2026.3.2p1. Faster pacing still requires headset validation.
- Follow-up measurement on 2026-09-06 disproved smoothing with max(new anchor, previous interpolated estimate): it added up to 1.083s above Position + LastUpdated age. Replacing every heartbeat anchor then caused visible backward flicker. For repeated integer Position while playing, preserve interpolation only inside that confirmed second; never enter the next second until Windows reports it. New positions, state/rate changes and seeks reanchor without carrying a previous lead. Freshness remains bounded. Fractional source positions use ordinary bounded interpolation. The user confirmed no flicker and correct synchronization at offset zero after this correction.
- The user requested automatic offset adjustment, then explicitly chose to correct and test the playback clock first. The clock correction is automatic. Audio capture/alignment and automatic repair of inaccurate provider timestamps remain outside this MVP; no hidden per-song offset is introduced.
