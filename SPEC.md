# LyricsChatbox MVP

## v0.2.0 approved extension
The frozen v0.1.0 release is commit 0bfdc91347f6c9642f70bc4f6057d15ff638540c. v0.2.0 evolves the same playback clock, epoch guard and 1.05s text scheduler. The user explicitly authorizes v0.1.0 publication and v0.2.0 publication only after its critical physical gates.

- Automatic display defaults to `{lyrics}`. Composer presets: Lyrics Only, Song + Lyrics (`♫ {title} — {artist}` then `{lyrics}`), Status / Time (`{message}` then `{time}`), Custom. Supported tokens: lyrics/title/artist/album/time/message/elapsed/duration. Time is local HH:mm; elapsed/duration are m:ss (h:mm:ss when needed). Template is bounded to 512 characters; missing fields and unknown tokens are omitted, empty lines and adjacent dangling separators cleaned. Substituted data is never interpreted as another template. UI shows visible final preview and actual payload usage.
- One manual/automatic ownership state controls the existing scheduler. Focusing/editing a draft takes Manual ownership. With live edit off, editing suppresses automatic sends but sends no draft until Send. Live edit keeps only the current draft, paced at the existing interval. Send holds the final manual text for 8s starting after it is emitted, then resumes current automatic state. Resume Automatic explicitly cancels the override; no automatic backlog exists. Clearing sends an ordinary empty message. Drafts/history are not persisted; custom status and templates are explicit saved settings.
- Typing is independent of text pacing: while focused and recently edited (3s), optional `/chatbox/typing` true refreshes every 2s. Send, clear, focus loss, idle timeout, automatic resume, disabling and shutdown clear typing best-effort. Receiver/destination changes reset typing dedupe. Master switch gates both manual and automatic text plus typing. Live edit, typing and compact default off for migration safety.
- Compact/Floating is an opt-in final formatting strategy for all nonempty text. Independently test suffix U+0003 U+001F; reserve its two UTF-16 units before grapheme-safe truncation. Empty clears have no suffix. Payload-based dedupe notices mode changes; preview omits suffix. It depends on client rendering, and cannot be considered visually validated or released as final until user confirmation.
- LRCLIB remains primary, local import still has priority over cache. Direct results must contain usable timed lines (or be instrumental); unusable direct content falls through to search. At most one additional album-filtered search is allowed when the broad result page is full (20 records) and no confident timed result exists. All candidates use the same strict title/artist/version/duration evaluator; no widened duration tolerance or speculative parallel requests. Missing/unavailable/429 remain distinct; transient failures are never remembered as permanent misses.
- Secondary remote provider is pending access/use compatibility. Current Musixmatch official docs require an API key, view tracking, copyright and branding when displaying lyrics (https://docs.musixmatch.com/getting-started ; https://docs.musixmatch.com/implementation-guidelines ; https://docs.musixmatch.com/lyrics-views-tracking). No key or applicable agreement is configured; do not add tracking, scraper endpoints or an advertised nonfunctional provider. Keep the existing resolver boundary until a supported integration fits the approved scope.
- v0.2 release adds focused tests for composer, ownership, typing/live-edit, appearance payload budgets/dedupe, migration and LRCLIB misses; representative native playback checks and a focused headset matrix (composer/manual/typing/live edit/compact/unicode) are required before final tag/release.

## Product and scope
A small Windows-only .NET 10 C# WPF application reads native Apple Music via Windows.Media.Control/GSMTC, resolves line-synchronized lyrics, follows the authoritative playback timeline, and sends the current line to VRChat OSC. No accounts, credentials, telemetry, backend, other players, scraping, private Apple APIs, word karaoke, or plugin framework. Independent implementation; no MagicChatBox source.

Single compact window: enabled control, source/track/artist, lyric, resolution status, offset (-5 to +5 seconds, positive means later: lyricTime = playbackPosition - offset), OSC host/port and concise degraded/error state. Settings persist locally; invalid settings fail safely; UI/network never block monitoring.

## Boundaries and responsibilities
AppleMusicPlayback enumerates and explicitly identifies sessions (never blindly current session). Preserve session identity, raw title/artist/album/track number, start/end/duration, reported Position, LastUpdatedTime, state/rate and local observation time. Keep normalized matching separate.

SynchronizationEngine uses authoritative anchors plus bounded monotonic interpolation; never accumulate timer deltas indefinitely. Paused playback freezes. Reevaluate on pause/resume/seek/restart/track change/discontinuity. Production timing/cadence decisions require actual Apple Music spike evidence. Missing/stale/unusable position fails closed.

Monotonically increasing track epoch invalidates lyrics before starting a new lookup. Session loss also invalidates. Async completions carry their initiating epoch; old success, error and cancellation cannot mutate the new track. Rapid changes and unchanged-track replay must be safe; reuse loaded lyrics where practical. Clean subscription/task disposal.

LyricsResolver order: exact local track-bound .lrc, validated flat cache, LRCLIB direct lookup, conservative search/scoring, no synchronized lyrics. Only timestamped lines qualify; instrumental and no lyrics are normal states. Normalize Unicode, case, spacing, punctuation and feature notation; preserve version annotations. Reject incompatible artist, duration or recording version and ambiguous candidates. Title alone is insufficient. LRC supports common timestamps, multiple tags, stable sorting, blank gap markers and metadata ignoring. Finite hold policy prevents lyrics hanging through instrumental gaps.

LRCLIB uses HTTPS, identifying User-Agent, sequential requests with spacing, bounded response/time, cancellation and Retry-After cooldown. Only necessary track metadata leaves the machine. Transient failure must not poison later tracks. Cache successes; corruption cannot prevent startup. Settings/cache under LocalAppData; no persistent full lyric history logs.

ChatboxOutput: default 127.0.0.1:9000, /chatbox/input (text, true, false). Preserve Unicode, conservatively cap at 144 UTF-16 units without splitting grapheme clusters, limit explicit lines, coalesce latest valid state, dedupe and pace sends. No stale retry queue. Disabling stops future lyric output immediately. UDP send success does not prove receiver presence or display. Receiver loss must not crash or build backlog; recovery sends current state only. Physical clearing/counting/pacing require client validation; tunables remain isolated.

## Primary contracts (checked 2026-09-05)
- Microsoft timeline: Position is current as of LastUpdatedTime: https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessiontimelineproperties
- LRCLIB: /api/get title+artist, album/duration recommended (duration 1–3600, ±2s matching); /api/search at most 20 records. 429 Retry-After; sequential 200–500ms spacing and User-Agent: https://lrclib.net/docs
- VRChat endpoint/144 characters/9 display lines: https://docs.vrchat.com/docs/osc-as-input-controller ; default receive port 9000: https://docs.vrchat.com/docs/osc-overview . These pages do not specify exact Unicode counting, empty-message clearing or a numeric pacing guarantee.

## Decisions from the native spike
- Apple Music 1.1540 exposes source `AppleInc.AppleMusicWin_nzyj5cx40ttqa!App`. On two observed tracks, `Artist` is `artist — album`, `AlbumTitle` empty and TrackNumber 0. Split only one exact spaced em dash when AlbumTitle is absent; retain raw values.
- Normal playback emits timeline events about every 280ms (sometimes duplicates), with whole-second Position. The sampled timeline age during a 19s playing segment was 0.015–0.280s. Use 250ms fallback polling plus event wakeups, a 2s freshness horizon and a 1.25s quantization/discontinuity tolerance. Paused anchors ignore timestamp age; resume must reject an old paused timestamp until refreshed. These choices need seek and longer end-to-end validation.
- GSMTC TryChangePlaybackPositionAsync returned true for forward/back/restart without changing playback. The product only observes playback; physical seek testing must use Apple Music controls. Do not interpret a successful control call as an observed transition.
- OSC uses a narrow fixed-message encoder (aligned UTF-8 address/type/text with payload-free T/F tags), because this is smaller than a general OSC dependency. OSC format checked against https://opensoundcontrol.stanford.edu/spec-1_0.html ; no third-party implementation copied. UTF-8 is a receiver compatibility requirement beyond the old OSC 1.0 ASCII text wording. A 10s line-hold cap remains provisional. Output pacing was reduced from 1.5s to 1.05s after the user reported 1–2s transition delay. The 2026.2.1 live release documents five messages per five seconds; 1.05s spacing stays below that rate even without relying on the automatic-send exemption: https://docs.vrchat.com/docs/vrchat-202621 . Installed client is 2026.3.2p1. Faster pacing still requires headset validation.
- Follow-up measurement on 2026-09-06 disproved smoothing with max(new anchor, previous interpolated estimate): it added up to 1.083s above Position + LastUpdated age. Replacing every heartbeat anchor then caused visible backward flicker. For repeated integer Position while playing, preserve interpolation only inside that confirmed second; never enter the next second until Windows reports it. New positions, state/rate changes and seeks reanchor without carrying a previous lead. Freshness remains bounded. Fractional source positions use ordinary bounded interpolation. The user confirmed no flicker and correct synchronization at offset zero after this correction.
- The user requested automatic offset adjustment, then explicitly chose to correct and test the playback clock first. The clock correction is automatic. Audio capture/alignment and automatic repair of inaccurate provider timestamps remain outside this MVP; no hidden per-song offset is introduced.
